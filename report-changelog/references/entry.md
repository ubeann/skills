# The entry

One folder per change, in the project:

```
docs/changelog/
  2026-11-07-shipment-lines/
    changelog.json      the source: context, copy per language, screenshot paths
    capture.mjs         the screens and the states that prove the change, re-runnable
    shots/before/*.png  captured before the first edit
    shots/after/*.png   the same script after the change
    evidence/*.png      what the request came with: chat screenshots, error pages, what the PIC saw
    README.md           generated by render.mjs: the backtrack record, readable on the forge
    out/                generated outputs, not committed
CHANGELOG.md            one line per entry, newest first
```

Add `docs/changelog/*/out/` to `.gitignore`. Outputs are re-rendered from the entry in seconds, so only the source and the shots are kept. A project with its own changelog file or docs folder names it in its agent doc, and that wins over these defaults.

The changelog line links the entry and the PR:

```
- 2026-11-07 · copy · [Vendor Lines → Shipment Lines](docs/changelog/2026-11-07-shipment-lines/) · #189
```

## changelog.json

`references/example.json` is a complete entry. The fields:

| Field | What |
|---|---|
| `slug`, `date` | the folder name's parts; `date` is `YYYY-MM-DD`, the day the change shipped |
| `project`, `module` | the eyebrow; the product's own names, as the reader says them |
| `type` | `copy`, `ui`, `fix` or `feature`; the cover's badge: grey, blue, red, green |
| `langs` | every language the reader needs, in order; the first one writes README.md unless `context.lang` says otherwise |
| `context` | the backtrack record, in one language, written only into README.md; see below |
| `head.<lang>` | `title` (a string, or `{old, new}` for a rename), `meta` (the screens it touches), `summary` (at most three `{label, text}` cards), `footer` (what did not change, in the reader's words) |
| `sections[]` | one per screen, plus one table for text that is not on any screen |
| `labels.<lang>` | overrides for the built-in `en` and `id` labels, or the labels of another language |

A section is one of three kinds. The screenshot paths sit on the section, shared by every language; the words sit under `text.<lang>`:

| `kind` | Fields | Use for |
|---|---|---|
| `pair` | `before`, `after` | a screen that existed before: copy, UI and fix changes |
| `single` | `shot`, optional `tag` | a screen that is new: a feature, with `steps` for how to reach and use it |
| `table` | `text.<lang>.rows` as `[where, before, after]`, optional `columns` | wording in guides, messages and emails that no screenshot shows |

Each section's `text.<lang>` has `title`, `where` (the breadcrumb a user follows to reach it), and `bullets` or `steps`. Write `**label**` around the app's own words; they stay in the app's language in every locale, so the reader can find them on screen.

## context

The repository's record, for whoever traces this change later; the stakeholder's outputs never show it. Write it for a developer: file paths, branches and commits belong here and nowhere in the report. Every field is optional. Fill what the conversation, the PR, the ticket or the user supplied; leave the rest out. An empty field is honest, while a guessed PIC or reason misleads the person backtracking later.

| Field | What |
|---|---|
| `lang` | the language the context is written in |
| `background` | how things were before and why that mattered |
| `reason` | why this change, and why now |
| `source[]` | `{kind, ref, note}`: where the request came from (a chat, a ticket, an incident) and the session or thread the work was done in |
| `people[]` | `{role, name}`: the PIC, the requester, the approver, who implemented it |
| `decisions[]` | `{question, chosen, options, by, why}`: each fork, what was picked over what, by whom |
| `scope` | `{pr, branch, commits, files}`; a commit is `{sha, subject}` or a bare sha. Record every commit and file: the context page shows at most six of each, folds files into their folders past that, and moves a big scope to a full-width card; README.md keeps the full lists folded in `<details>` |
| `verification[]` | how it was checked |
| `unchanged[]` | what a reader might fear changed and did not: data, calculations, output files |
| `risks[]`, `followups[]` | what is left |
| `rollback` | how to undo it |
| `evidence[]` | `{file, what, from, date, thread}`: one per image in `evidence/`; `what` says what it shows ("PIC asks to rename the field", "500 on order status update"), `from` who sent it, `thread` the session it was attached in |
| `extra[]` | `{label, text}` for anything else the user gave (a deadline, a client, a related incident) |

## Evidence

Evidence is what the change was asked or reported with, kept so the chat can be recalled when the change is questioned later. Screenshots the agent took of the app are `shots/`, never evidence.

- **Where attachments live.** In T3 Code, every image attached to a thread is `~/.t3/userdata/attachments/<threadId>-<attachmentId>.<ext>`, and the current message names its path. For a change discussed across threads, read each thread named as a source with `t3_thread_read` and take its attachments the same way. Elsewhere, the path is in the message that attached the image.
- **Name it** `NN-<what>.<ext>` in the order it happened: `01-pic-request.png`, `02-prod-error-500.png`.
- **Keep it in a private repository only.** Chat screenshots carry names, phone numbers and customer data. In a public repository add `docs/changelog/*/evidence/` to `.gitignore` and tell the user the evidence stays local. When an image shows unrelated customer data, crop it to the part that matters before saving.
